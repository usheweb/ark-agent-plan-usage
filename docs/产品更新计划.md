## 0. 一句话定位（演进方向）

| | 定位 |
|---|---|
| 现在 | 火山方舟 Agent Plan 余量查看器（**单场景**、UI 写死） |

## 1. 本次产品讨论（2026-10-14）

### 1.1 背景与问题

- **现状**：产品只服务「火山方舟 AFP」一种数据。取数逻辑（`GetAFPUsage`）与界面（近 5 小时 / 近 1 周 / 近 1 月的圆环卡片）都是方舟专属、写死的。
- **用户诉求**：不只做方舟一种数据的查看；希望做成**多场景**——用户自己录入不同平台的 Key，选择要看的场景，支持看一个或同时看多个，**不同场景有各自定制的悬浮窗 UI**。
- **窗口尺寸**：当前两种形态尺寸写死（普通 420×500、悬浮 236×100，均带最小尺寸约束），两种形态都要支持**用户自定义大小**。

### 1.2 截图两个红框区域的复用思路

用户标注的 2 个区域可以作为「不同场景 / 不同类型产品」复用的落点：

- **区域① 顶部标题栏（`.topbar`）**：现状 = 品牌图标 + 标题「火山方舟 AFP 用量 / Agent Plan 套餐额度」+ 档位徽标（Medium 档）+ 设置 / 刷新。
  → 可扩展为：**场景标识（名称 / 图标）+ 场景切换** + 当前场景的专属徽标 + 通用操作（设置 / 刷新）。
- **区域② 数据卡片区（`#cards`）**：现状 = 三个圆环卡片。
  → 可扩展为：**当前场景的数据视图**，每个场景有自己的形态（圆环 / 数字 / 进度条 / 列表 / 图表等）。
- **悬浮窗**：同样按此思路 —— **可调整大小**，**不同场景有各自的 UI**。

> 注：红框②未覆盖到「更新于 13:29:12 / 44s 后自动刷新 / 定住」那一行（在两个红框之间的状态条 `.status-bar`），该行属于通用状态区，不随场景变化。

### 1.3 核心抽象

把「场景」抽象为**可插拔的数据源适配器**：

```
Scenario = {
  标识/名称,          // 场景身份
  凭证 (Key/Token),   // 每个场景独立
  取数逻辑,           // 如何拉数据（内置适配 or 自定义配置）
  指标定义,           // 这个场景要展示哪些数值
  专属 UI 模板        // 在卡片区 / 悬浮窗里怎么画
}

窗口 = 承载 1..N 个场景视图的容器，尺寸 / 位置可自定义并记忆
```

### 1.4 场景形态候选（待收敛）

- **A. 内置平台（官方适配）**
  - 火山方舟 AFP（现有）
  - 其它大模型平台的用量 / 余额：OpenAI、Anthropic、DeepSeek、智谱、Kimi、通义、Gemini…
- **B. 自定义数据源（用户自配）**
  - 通用 HTTP：URL + Method + Headers/Auth + **JSONPath 取值映射** → 自动生成卡片
  - 本地脚本 / 命令：执行命令读取输出（进阶）
- **C. 其它**：云资源额度、订阅制服务的剩余额度等

### 1.5 关键设计问题（开放讨论，待定）

1. **多场景同屏方式**（三选一或组合）：
   - (a) 单窗口内**多卡片堆叠**
   - (b) 单窗口内**标签页 / 轮播切换**
   - (c) 每场景一个**独立悬浮窗**（多窗口）
2. **同时展示数量上限**：建议软上限（如 6），超过则折叠 / 轮播。
3. **窗口自定义尺寸的记忆粒度**：全局一套，还是每个场景 / 每个窗口独立记忆？
4. **悬浮窗形态**：现在是固定单卡片（236×100）。多场景时是「多卡片堆叠的**可缩放**窗口」还是「单卡片**轮播**」？
5. **凭证安全**：当前明文存 `credentials.json`；多场景后建议接入系统钥匙串 / 加密。
6. **刷新策略**：全局统一，还是每个场景独立间隔？
7. **命名 / 品牌**：`productName` 已由「AFP用量」改为 **「唐三浪悬浮窗」**（决策 Q7，见待办 E-04）。

### 1.6 建议落点（截图红框 → 设计映射）

| 区域 | 现状 | 多场景后的建议 |
|---|---|---|
| ① topbar | 品牌 + 档位徽标 + 设置/刷新 | 左侧「场景标识（图标 + 名称，可点切换）」；右侧保留当前场景专属徽标 + 设置/刷新；多场景时加一排场景 tab / 小圆点 |
| ② 卡片区 | 3 个圆环卡片（方舟专属） | 渲染「当前场景」的 UI 模板；多场景同屏时按顺序堆叠，每块一个场景视图 |
| 悬浮窗 | 固定 236×100 单卡片 | 可拖拽调整大小；小尺寸下轮播 / 只显示选中场景，放大后堆叠；位置 + 尺寸均记忆 |
| 状态条 | 更新于 / 倒计时 / 定住 | 保持不变（通用，不随场景变化） |

## 2. 版本规划（草案）

### v0.1.x —— 单场景，收尾中
- 火山方舟 AFP 用量（近 5 小时 / 近 1 周 / 近 1 月）
- 悬浮窗：定住 / 取消、**位置记忆**、取消定住后**自动回到可视区**
- 余量颜色分档（绿 / 蓝 / 橙 / 红）
- Windows 适配（四角、Win+D 隐藏拦截）

### v0.2 —— 多场景架构（下一个大版本）
- 引入 **Scenario 抽象 + 场景注册表**
- **场景管理 UI**：增删场景、录入各自 Key、启用 / 停用
- **多场景同屏**：先做「单窗口堆叠 + 轮播切换」
- **窗口尺寸自定义 + 尺寸 / 位置记忆**
- topbar 场景标识与切换
- v0.1 方舟凭证 / 配置的**平滑迁移**

### v0.3 —— 自定义数据源 + 更多内置平台
- 通用 HTTP / JSONPath **自定义场景**配置界面
- 内置 2~3 个常见平台适配
- 场景 **UI 模板库**（数字 / 进度 / 列表 / 图表）

### v0.4 —— 进阶
- 多窗口独立悬浮（方案 c）
- 凭证加密 / 系统钥匙串
- 主题 / 透明度 / 字体缩放
- 命名与品牌通用化

## 3. 技术方向备忘（非本次实现，仅记录思路）

- **前端**：新增 `ui/sources/` 注册表，每个 source 导出 `{ meta, credentialSchema, fetch, renderCards, renderFloat }`。
- **后端**：把写死的 `GetAFPUsage` 改为通用逻辑（trait 适配器，或通用签名 / HTTP 代理），由前端驱动取数。
- **配置**：单一 `config.json` = `{ scenarios: [...], display: { size, position, visible } }`；凭证独立存储。
- **兼容**：v0.1 的方舟凭证与配置需能平滑迁移。

## 4. 风险与注意

- 多平台接口差异大（签名方式、限流、字段），**维护成本高** → 用「自定义 HTTP」兜底，内置平台只做精选。
- **UI 定制边界模糊** → 先固化「模板 + 数据映射」，而非完全自由的画布。
- **凭证安全合规**：多凭证后明文存储风险放大。
- **窗口尺寸自由化**与现有固定尺寸 / 最小尺寸 / clamp 逻辑冲突，需要**重构尺寸策略**。
- 多场景同屏会放大悬浮窗体积与刷新开销，需要上限与节流策略。
