# 平台对接清单（Platform Integration Backlog）

> 产品目标：**在一个悬浮窗里看全部关注的数据**。本清单记录**可对接的平台、取数方式与接入待办**，是 [待办清单](./待办清单.md) 第三节「自定义数据源 + 更多平台」的展开明细。
>
> **产品定位**：面向**预付费账户**——凡是需要先充值 / 买资源包才能用的互联网服务，余额见底都会直接导致业务停摆。本产品要把这些分散在各家控制台里的余额，收敛到一个悬浮窗里盯住。
>
> **分工原则**：**原生适配只做头部平台**（第一 / 第二梯队，接口稳定、用户量大）；长尾平台走 [待办清单](./待办清单.md) C-01「通用 HTTP 自定义数据源」兜底，不逐个手写适配。因此第七节的候选池**不要求全部原生实现**，它是一份「谁值得做」的取材范围。
>
> 方向与架构讨论见 [产品更新计划](./产品更新计划.md)。
>
> **优先级**：P0 > P1 > P2 ｜ **状态**：待办 / 进行中 / 已完成 / 待定 / 不做 / 待核实
> 最近更新：2026-10-15

> 「未核实」= 没找到官方文档，**不代表一定没有**；后续如发现官方接口可上移到第一 / 第二梯队。

## 五、接入前必须先统一的三个抽象（跨平台共性）

1. **数据形状 → 每平台独立 UI（已拍板）**：账户余额（钱）/ 套餐额度（AFP、Token Plan）/ 用量与成本（账单类）**不做强行统一模板** —— 接口是独立对接的，UI 也随平台一起单独设计。**只共用「窗口壳」**：topbar / 场景 Tab / 设置弹窗 / 刷新按钮 / 悬浮窗容器，平台自己的展示区各自实现。
2. **凭证类型**：Bearer Key / AK-SK 签名 / HMAC / OAuth / 管理密钥 → 统一凭据存取（计划进系统钥匙串）并按场景索引，见 [待办清单](./待办清单.md) M-03、E-01。
3. **刷新粒度**：实时额度 vs 日结账单 → **每场景独立刷新间隔**，见待办清单 E-02。

对应架构待办：M-01（Scenario 抽象 + 场景注册表，**每个 source 自带取数与 UI**）、M-03（多凭证）、E-01（钥匙串）、E-02（独立刷新间隔）。
